# Agent类修改
本系统中的skills以langgraph中的节点方式进行嵌入，在Agent类（agent文件夹下的内容，开发时使用的是dsda和dsds）中通过构建**_node_query_skills**节点实现模块化嵌入，对该类其他内容并无修改（连函数都是内嵌的）

# 状态类修改
因为需要重复调用Agent中的state类，若保持和之前一样和agent放在同一个文件中书写可能存在循环导包的问题，因此在本轮开发中将状态类和agent类分开，dsds.py中写了对于langgraph运行时的state内容，该代码来自于原本文件中的state，并且添加了面向A2A对话的相关内容，运行逻辑与源代码没有区别

环境构建和技能开发详见 openskills集成流程 ,在此不再赘述

除去openskills本身的技能以外，本轮开发中还涉及了skills与大模型结合的方法，在skills文件夹中

# 环境变量的获取
原本src项目中获得相关环境变量的方法是通过在根目录下构建一个yaml文件，将所有的变量存储在文件中，然后构筑专门的config方法，从中获取相关内容

但是这种方法在skill中存在冲突，原因如下：

1.openskills注重方法的模块性，建议所有的技能相关内容全部都在.claude/skills/<skill_name>中保存，不建议从根目录或者其他地方调取。

2.在系统中不论是使用命令行命令或者方法调用，都需要通过在根目录下访问技能中scripts文件夹下的内容，但由于.claude文件夹是由.开头，对ubuntu来说属于隐藏文件（也许是因为系统），在跨文件夹调用的时候存在很多问题。

3.尽管去掉文件夹前面的.可以解决问题2，但是破坏了原本的模块性，不好说是否会遇到其他强耦合的问题。

在本轮开发中使用的方法是通过Pathlib的parent方法来强制获得yaml文件中的信息（与app_config中某些方法一致）

# 技能使用方法
本轮开发中主要使用了俩个原创技能，分别是milvus_query和mysql_query，下面进行介绍

现在在langgraph中的调用是在chat之前添加了技能节点，也就是用户输入的内容会首先判断是否需要调用技能，如果不需要调用技能就直接返回langgraph的state，如果需要调用技能，就会在提示词模板中添加相关内容，最终技能获得的信息会和系统提示词模板一起输入大模型中进行推理。

这个过程符合Hooks + Commands + Agents 协同激活的思想，理由如下：

在文章中提到引入Hooks的作用是强制让大模型按照手册来执行任务，现在属于直接强行让模型判断是否使用技能而不是让大模型自己判断是否需要进入技能节点在判断是否使用技能

Commands是指给大模型明确指令时，模型需要参考某一份文件来执行过程，当前实现方法中，会让大模型返回openskills语句，这与Commands的方法一致。

对于各个技能的详细内容请参阅技能文件夹下的SKILL.md文件
